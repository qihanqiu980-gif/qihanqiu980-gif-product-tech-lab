建立任务：先问“我要证明什么”

把今天的技术学习固定在一个真实产品问题上。你不是来背名词，而是要判断页面变化、业务事实与证据之间的距离。

04 MIN
学习工作区
本节结论

验收前先把问题写成“观察对象＋期望变化＋证据边界”。页面看起来成功，只能说明可见界面发生了变化；要证明真实报名成立，还必须找到后端校验和保存记录。

任务现场：年龄报名规则PRODUCT SCENARIO

需求写着：“未满 18 岁不能报名，年满 18 岁可以报名。”页面上有年龄输入框、报名按钮和结果提示。17 岁时按钮不可用，改成 18 岁后按钮可用，点击后出现“报名成功”。

这段现象至少包含三层问题：浏览器是否正确展示规则；前端是否正确处理输入与状态；服务端是否重新校验并真的保存报名记录。三层问题需要不同证据，不能用一张成功截图一次性代替。

  • 1观察对象：年龄输入、按钮状态、提示文案、请求结果和保存记录。
  • 2期望变化：17 岁被阻止，18 岁可提交，合法请求得到明确反馈。
  • 3证据边界：页面证据说明“看见什么”，服务端证据说明“业务是否真正成立”。
今天要能证明

你能说清网页由哪些角色协作完成，点击以后页面为何变化，以及当前截图、状态或实验分别支持哪一层结论。

今天不会假装证明

完成一次小游戏、看到一次成功提示，都不等于长期掌握，也不等于数据库保存、资格规则不可绕过或线上系统绝对可靠。

产品经理怎么用

写验收点时，不只写“显示报名成功”，还要拆成输入条件、交互反馈、提交结果、异常处理和可信证据。这样研发、测试和产品讨论的是同一件事。

SESSION 01 · CHAPTER 02

模型一：浏览器如何形成网页

先分清运行环境、用户看到的页面，以及被浏览器读取并执行的前端材料。三者关系清楚，后面的交互链才不会混成一团。

10 MIN
模型精讲
核心结论

浏览器是运行和呈现环境，网页是用户此刻看到并可操作的结果，前端代码是浏览器用来生成这个结果的材料与指令。文件本身不是网页，网页也不是浏览器。

浏览器 Browser

安装在设备上的软件，例如 Chrome、Safari。它读取网络响应或本地文件，解析代码、执行脚本、绘制界面并接收用户操作。

运行位置：用户设备。易混点：它不是某个具体网页，也不是业务数据库。
网页 Web Page

浏览器根据代码、数据和当前状态形成的可见、可交互结果。标题、输入框、按钮、提示与布局都属于页面体验的一部分。

输出位置：浏览器窗口。易混点：截图只是某个时刻的表象。
前端代码 Frontend Code

发送到用户设备并由浏览器处理的 HTML、CSS、JavaScript 等资源。它们定义结构、样式、交互和部分校验。

输入来源：服务器或本地。易混点：前端代码可被查看和修改，不能独自守住可信规则。
输入—处理—输出
输入

URL、HTML/CSS/JavaScript 文件、图片字体、接口数据、设备环境与用户操作。

处理

浏览器下载资源，解析结构和样式，执行脚本，计算布局，再把像素绘制到屏幕。

输出

一个当前时刻的网页：既包括可见界面，也包括可被脚本更新的内部结构与状态。

完整示范：打开报名页FROM URL TO PAGE
  • 1用户输入报名页地址。浏览器向服务器请求资源，这是一次“要什么”的输入。
  • 2服务器返回 HTML、CSS、JavaScript 和初始数据。它们仍是材料，不是用户已经看到的页面。
  • 3浏览器解析 HTML 得到结构，计算 CSS 得到呈现规则，执行 JavaScript 建立交互与当前状态。
  • 4浏览器绘制年龄框、按钮和说明，网页才成为可见结果。不同屏幕尺寸可能得到不同布局。
  • 5用户输入 17。浏览器接收新操作，前端代码可能更新按钮状态；此时没有必然发生服务器保存。
运行差异推演
资源只到一半

HTML 和 CSS 已加载，但 JavaScript 请求失败时，页面可能看起来完整，按钮却没有反应。此时“看得见”不等于“功能资源都已运行”，应补看网络资源和控制台错误。

环境并不相同

同一批前端代码会受到浏览器版本、屏幕宽度、字体和能力支持影响。桌面 Chrome 正常，只能证明这个组合；移动 Safari、键盘操作和弱网仍需分别观察。

页面先于数据出现

浏览器可以先画出结构，再等待报名数据返回。空白、加载中和真正无数据是三种状态，产品文案与验收步骤要把它们分开，避免把等待误判成内容丢失。

当前证据可以证明

页面已在某浏览器和设备上被正确加载；某些资源成功运行；当前可见结构、样式和交互状态符合观察。

当前证据不能证明

所有浏览器都一致、网络异常时仍正常、服务端规则不可绕过，或页面提示背后的数据库事实一定成立。

常见误解：网页就是一份 HTML 文件

纠正：HTML 只提供结构基础。真实网页还受到 CSS、JavaScript、接口数据、浏览器能力和当前状态共同影响。同一份 HTML 可以呈现出不同外观和行为。

产品经理怎么用

遇到“页面打不开”时先区分：是浏览器兼容、资源加载、代码执行、接口数据还是页面设计问题。清楚运行层次，才能给研发提供可定位的现象，而不是笼统说“网页坏了”。

扩展边界：缓存为什么会让两个人看到不同页面？

浏览器可能保留旧的前端资源，服务器也可能按用户、地区或实验分组返回不同内容。因此验收记录要带上浏览器版本、时间、账号和刷新方式。这个边界重要，但不进入本节必答门槛。

SESSION 01 · CHAPTER 03

模型二：HTML、CSS、JavaScript 如何协作

三类前端代码不是三个互不相干的文件。它们围绕同一页面对象分工：先有可识别结构，再有呈现规则，最后用逻辑响应变化。

14 MIN
模型精讲
核心结论

HTML 回答“页面里有什么以及它们是什么”，CSS 回答“这些内容如何呈现”，JavaScript 回答“遇到输入后如何计算和改变”。三者协作，但不能互相替代。

HTML

用有语义的元素描述内容结构，例如标题、表单、标签、输入框和按钮。结构让浏览器、键盘和辅助技术知道每个部分是什么。

主要输出：DOM 的初始骨架。易混点：HTML 能声明基础约束，但不是完整业务逻辑。
CSS

为结构指定颜色、字号、间距、布局、可见性和不同屏幕下的呈现规则。它决定“怎么被看见”，也能表达禁用或错误状态的外观。

主要输出：视觉与布局规则。易混点：灰色外观不等于控件真的不可操作。
JavaScript

读取事件和数据，执行条件判断，更新页面状态，并要求浏览器修改结构、属性或样式。它让静态页面形成连续交互。

主要输出：行为与状态变化。易混点：前端脚本可被绕过，不能承担最终可信裁决。

输入

产品规则、内容层级、视觉规范、用户事件、接口数据和已有页面状态。

处理

HTML 提供对象，CSS 匹配并呈现对象，JavaScript 读取对象与输入并计算下一状态。

输出

具有结构、外观和响应能力的页面；每次状态改变都可能触发新的 DOM/CSS 呈现。

完整示范：17 岁到 18 岁ROLE BY ROLE
  • 1HTML：建立“年龄”标签、数字输入框、报名按钮和结果提示区域。标签与输入框关联，按钮有明确类型。
  • 2CSS：让表单层级清楚；正常按钮使用橙色，禁用按钮降低对比；错误提示不仅变红，还带有文字说明。
  • 3JavaScript：监听输入事件，将文本转换为年龄，判断是否大于等于 18，再更新按钮的禁用属性与提示状态。
  • 4浏览器：根据更新后的 DOM 属性和 CSS 规则重新绘制。用户看到按钮从不可用变为可用。
  • 5提交时：JavaScript 可以发送请求并显示响应，但后端仍需独立校验年龄，不能相信前端已经检查过。
同一需求的三层验收
验 HTML

先检查年龄标签是否与输入框关联、按钮类型是否正确、提示区域能否被辅助技术读到。结构正确意味着对象和语义可识别，不意味着视觉或逻辑已经完成。

验 CSS

再检查正常、禁用、错误、聚焦和窄屏状态。颜色只是一个信号，文字、边框和控件属性也要共同表达状态，避免色弱用户或键盘用户失去反馈。

验 JavaScript

最后用空值、17、18、19 和重复修改检验逻辑，观察事件是否触发、旧提示是否清除、状态是否一致。三层单独通过后，还要再跑一次完整协作路径。

当前证据可以证明

语义结构存在、视觉状态符合规范、事件触发后前端逻辑得到预期页面结果；还可检查键盘与不同屏幕表现。

当前证据不能证明

只看 CSS 不能证明按钮真被禁用；只看 JavaScript 不能证明请求一定被服务端接受；只看 HTML 不能证明交互完整。

常见误解：把按钮涂灰就等于禁用

纠正：CSS 只改变外观。真正的前端禁用通常还要设置按钮属性、阻止事件路径并给出可访问说明；即使这些都做了，服务端仍要重新校验。

产品经理怎么用

评审交互稿时分别询问：结构是否有明确语义？不同状态如何呈现？什么事件触发什么逻辑？不要用“前端做一下”把三类工作混为一句模糊要求。

扩展案例：没有 JavaScript，网页就完全不能交互吗？

不是。HTML 本身支持链接、表单提交、展开控件等基础交互，CSS 也能响应悬停和焦点。JavaScript 的价值在于复杂条件、局部更新和状态协同。这个例外提醒我们不要把职责说成绝对排他。

模型三：事件、状态与 DOM 如何驱动交互

页面变化不是按钮自己“知道该怎么做”。变化来自一条可追踪的链：事件带来输入，JavaScript 计算新状态，DOM/CSS 把状态呈现出来。

14 MIN
60 秒闭卷启动

先回忆，再阅读

遮住第一时段内容，口头回答：浏览器运行什么形成网页？三类前端代码如何分工？页面成功为什么不等于业务成功？答完再进入下面的新模型。

模型精讲
核心结论

用户事件是变化的触发输入，页面状态是当前事实的前端表示，DOM 是脚本能够读取和修改的页面结构。JavaScript 把三者串起来，CSS 再根据结构和状态完成呈现。

DOM

浏览器把 HTML 解析成的对象结构。标题、输入框、按钮都成为可被 JavaScript 查找、读取和修改的节点。

角色：页面结构的运行时表示。易混点：DOM 不是原始 HTML 文本，也不是数据库。
用户事件 User Event

用户点击、输入、聚焦、提交或按键后，由浏览器产生的信号。事件包含发生对象和相关信息，是交互链的起点之一。

角色：输入信号。易混点：发生事件不等于处理逻辑一定成功。
页面状态 UI State

页面当前需要记住的值，例如年龄、是否符合资格、请求是否进行中、提示类型。状态决定此刻应该呈现什么。

角色：当前结果。易混点：刷新可能丢失，且不等于服务端持久数据。
输入

点击或输入事件、当前状态、产品规则，以及可能返回的接口数据。

处理

JavaScript 读取事件和值，按规则计算下一状态，再修改 DOM 属性、文本或样式标记。

输出

浏览器重新绘制按钮、提示与布局；用户观察结果并可能产生下一次事件。

用链路定位故障
事件没有进入

输入后状态面板完全不变，先检查监听对象、事件类型和控件是否真的可操作。不要一看到“按钮没变”就直接认定年龄条件写错，因为输入可能根本没有到达逻辑层。

状态计算错误

事件已发生，但 18 岁仍得到 eligible=false，应检查值是否还是字符串、边界条件写成大于而非大于等于、旧状态是否覆盖新结果。这里的问题在处理而非呈现。

状态与页面脱节

状态已经是 true，按钮仍禁用，说明 DOM 属性或样式标记没有同步。反过来，按钮变橙但状态仍是 false，也会在下一次提交时暴露不一致。

当前证据可以证明

某事件被识别，JavaScript 得到了预期状态，DOM 属性和可见呈现随之变化；控制台或状态面板可加强因果证据。

当前证据不能证明

页面状态一定已持久保存、刷新后仍存在、其他设备同步，或绕过界面直接发请求时仍会执行同一资格规则。

常见误解：DOM 就是用户看到的像素

纠正：DOM 是结构化对象，CSS 和浏览器绘制把它变成像素。DOM 节点可以存在但不可见，也可能与屏幕上的视觉区域不一一对应。

产品经理怎么用

描述交互时写清“什么事件＋读取什么旧状态＋计算什么新状态＋页面哪部分更新”。这比“点一下变成功”更容易发现加载中、重复点击、错误恢复和空值等遗漏。

扩展边界：状态一定放在哪里？

小页面可能把状态放在 DOM 属性或简单变量里，复杂应用会使用框架或状态管理工具。具体存放方式可以变化，但“事件读取旧状态并产生新状态”的思考框架仍然有效。

SESSION 02 · CHAPTER 06

模型四：前端表现与可信业务裁决

前端负责及时、清楚地帮助用户完成操作；后端负责在可信环境中重新判断规则并保存事实。两者都做校验，但目的、可信度和证据不同。

12 MIN
模型精讲
核心结论

前端可以改善体验、减少无效提交并呈现结果，但运行在用户可控制的环境中；后端必须对关键规则做可信裁决。正确验收要让结论停在证据能够支撑的位置。

前端能力边界

前端擅长收集输入、即时反馈、页面导航、状态呈现和调用服务；但代码与请求可被查看、修改或绕过。

边界：能改善体验，不能单独保证关键业务真实性与安全。
前端校验

在浏览器内检查必填、格式、范围和明显冲突，让用户尽早知道问题，减少无效请求，例如 17 岁时提示未达门槛。

目标：快反馈与好体验。易混点：不是最终授权与可信规则。
后端校验

服务端根据可信数据和业务规则重新验证请求，决定接受或拒绝，并控制持久化、权限和一致性。

目标：业务正确与可信裁决。易混点：后端通过也不代表前端体验一定清楚。
输入

用户填写值、身份信息、请求参数、服务端可信数据、业务规则和当前资源状态。

处理

前端先做体验校验并发请求；后端独立校验资格、权限与一致性，再执行或拒绝操作。

输出

前端得到响应并呈现；后端留下状态变化、记录或明确错误，成为更强的业务证据。

三类失败要分别处理
前端误拦合法用户

18 岁用户因格式转换错误被按钮阻止，说明体验路径失败；即使后端规则正确，用户也无法正常提交。需要修复前端判断，并验证边界值和错误恢复。

后端接受非法请求

页面正常拦住 17 岁，但直接请求却创建了报名记录，说明可信裁决缺失。这是业务正确性问题，不能用“普通用户不会这么操作”降低优先级。

响应丢失造成重复

后端已经保存，网络中断让前端仍显示失败。用户再次点击可能重复报名。此时要检查幂等、查询恢复和文案，不应简单把按钮重新开放当作修复。

前端证据能证明

提示是否及时、控件是否正确、请求是否按预期发出、收到响应后页面是否正确恢复或更新。

还需后端证据证明

绕过页面仍会被拒绝、权限与资格按可信数据裁决、记录只创建一次、失败时没有错误写入。

常见误解：既然后端会校验，前端就不用校验

纠正：后端校验保障可信业务，前端校验保障及时体验和请求质量。二者常常验证同一规则，但服务对象不同，不能用一个替代另一个。

产品经理怎么用

在需求中标明哪些规则属于体验校验，哪些属于可信裁决；为异常响应定义清楚文案与恢复动作；验收结论注明证据来源，避免“页面成功＝业务成功”的越界表达。

扩展边界：后端返回成功就一定万无一失吗？

也不是。响应可能在持久化前错误返回，或后续流程失败。关键业务还可能需要数据库记录、幂等结果、审计日志或下游状态。证据强度要与结论风险匹配。
