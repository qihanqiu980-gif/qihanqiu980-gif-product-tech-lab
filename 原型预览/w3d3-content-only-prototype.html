SESSION 01 · CHAPTER 02

模型一：从业务问题到 WHERE 条件

数据库不能执行“帮我看看订单”。它需要你说明从哪张表开始、留下哪些行、输出哪些列。

14 MIN
Query Question

查询问题

写 SQL 之前，先把业务话压成一个有限问题。

查询问题是把“看一下订单”改写成一条 SQL 能回答的问题，通常包含对象、范围、条件和想看的列。

为什么需要它没有查询问题，SQL 会变成随便看表，结果也不知道是否回答了需求。

解决什么问题回答“这条 SQL 到底要验证哪个有限问题”。

输入
业务疑问和 orders 表字段。
输出
business_question 与 SQL 草稿。
责任人
学习者负责翻译问题。
不负责
不计算指标，不诊断数据质量。

产品经理怎样用：当同事说“帮我看一下支付订单”，你先把它改成“查看本地 orders 表中 status 为 paid 的订单号、用户和支付时间”。这样数据库才知道从哪张表、哪些行、哪些列开始。

正确例子业务问题：查看本地 orders 表中已支付订单的 order_id、user_id、paid_at。
越界例子业务问题：算出真实业务 GMV 并判断活动效果。这个问题需要聚合、口径和生产数据，不属于 W3D3。
WHERE Condition

WHERE 条件

FROM orders 之后的行级过滤门。

WHERE 条件用字段、比较符和值决定哪些订单行留下。它是选行，不是选列、排序或统计。

为什么需要它产品问题通常只关心某类订单；条件不清楚会混入无关行。

解决什么问题回答“哪些行应该进入这次结果，哪些行应该排除”。

输入
orders 候选行、字段、比较符和值。
输出
通过条件后的订单行集合。
责任人
学习者写条件，SQLite 逐行判断。
不负责
不负责排序、别名、去重、聚合或连接。

产品经理怎样用：产品经理说“只看已支付订单”，数据库听不懂这句中文；你必须翻译成 `WHERE status = "paid"`，让 SQLite 逐行判断 status 是否等于 paid。

正确例子`WHERE status = "paid"` 会留下 O1001、O1002、O1004 等 paid 行。
越界例子`SELECT status FROM orders` 只是展示 status 列，并没有筛掉 cancelled 或 pending 行。
Comparison Operator

比较符

把中文判断变成数据库能执行的符号。

比较符把字段和值连接成判断，例如 `=`、`!=`、`>=`、`<`，让 SQLite 知道怎样逐行判断真假。产品经理要把“等于、当天、晚于、早于”说成数据库能执行的符号。

正确例子`paid_at >= "2026-08-31" AND paid_at < "2026-09-01"` 会留下 8 月 31 日内的 paid_at 样本。
越界例子`paid_at = "昨天"` 不是稳定边界，也不能解释具体起止时间。
Text Value Filter

文本值筛选

status、channel 这类值需要引号。

文本值筛选是对 status、channel 这类文本字段使用引号包住的目标值进行行过滤。产品经理评审 SQL 时，要确认筛选的是字段里的文本值，不是一个不存在的字段名。

正确例子`WHERE channel = "app"` 会留下 channel 为 app 的订单，包括 O1001、O1003、O1004。
越界例子`WHERE channel = app`，SQLite 会把 app 当成字段名，查询会报错或无法得到预期结果。

同一个订单案例：从业务话到 WHERE

业务话
我想看已支付订单。
查询问题
查看本地 orders 表中 status 为 paid 的订单号、用户和支付时间。
SQL 条件
WHERE status = "paid"
预期留下
status 列等于 paid 的行；cancelled、pending、refunded 不应该留下。
实际看到
前 5 行为 O1001、O1002、O1004、O1006、O1007。
不能证明
不能证明真实生产支付订单数、收入或数据质量。
SESSION 01 · CHAPTER 03

模型二：日期边界、排序、别名和 DISTINCT

筛出行之后，还要决定时间窗口、展示顺序、列头和去重观察。这里仍然不是指标计算。

14 MIN
Date Range Boundary

日期范围边界

把“当天”写成明确起点和结束边界。

带小时分钟的 paid_at 不能只写 `paid_at = "2026-08-31"`。更稳妥的写法是 `paid_at >= "2026-08-31" AND paid_at < "2026-09-01"`。

正确例子Q3 预期留下 O1001、O1002、O1004、O1005、O1006 等 8 月 31 日样本。
越界例子没有结束边界就说这是完整当天，或把时区、延迟刷新也当成已验证。
Order Direction

排序方向

解释第一行为什么在前。

ORDER BY 决定展示先后。要说“最近支付订单”，必须写 `ORDER BY paid_at DESC`；LIMIT 只截取样本，不负责排序。

正确例子Q4 实际前 5 行为 O1019、O1014、O1018、O1018、O1013，说明结果按 paid_at 倒序展示。
越界例子没有 ORDER BY 却说第一行最新，或把前 5 行当作全量趋势。
Column Alias

列别名

让结果列头更适合交接。

AS 只改变这次查询结果的列名，不修改 orders 表字段本身。它的价值是让产品记录和同事交接更可读。

正确例子Q5 输出 `paid_at AS paid_time`，结果列头叫 paid_time，但原表字段仍叫 paid_at。
越界例子用 AS 后声称数据库字段已经改名。
DISTINCT Result

DISTINCT 结果去重

只观察不重复展示，不计算数量。

`SELECT DISTINCT channel FROM orders` 只能展示本地样本里出现过哪些 channel，不能说明每个渠道有多少订单。

正确例子Q6 实际看到 app、miniapp、web 三类 channel 取值。
越界例子说 DISTINCT 已经算出渠道订单数、渠道转化或渠道指标。

同一个订单案例：结果如何变得可读

业务话
我想看 8 月 31 日最近支付订单，列名要能交接。
SQL 组合
日期边界 + ORDER BY paid_at DESC + paid_at AS paid_time
预期留下
paid_at 在 2026-08-31 起点到 2026-09-01 起点之前的行。
实际看到
O1018、O1017、O1016 等行按 paid_time 倒序出现。
能证明
这条基础查询的时间边界、排序和列头可复核。
不能证明
不能证明收入正确、重复行来源、NULL 用户原因或渠道指标。

  1. 业务问题
    查看本地 orders 表中已支付订单的 order_id、user_id、status、paid_at。
    SQL
    SELECT order_id, user_id, status, paid_at FROM orders WHERE status = "paid" LIMIT 5;
    预期留下
    status 等于 paid 的行；cancelled、pending、refunded 不应留下。
    实际看到
    O1001、O1002、O1004、O1006、O1007。
    能证明
    WHERE 文本条件能筛出 paid 行样本。
    不能证明
    不能证明真实生产支付订单数、收入或状态字段没有脏值。
  2. 业务问题
    查看本地 orders 表中 channel 为 app 的订单样本。
    SQL
    SELECT order_id, channel, status FROM orders WHERE channel = "app" LIMIT 5;
    预期留下
    channel 等于 app 的行；web、miniapp 不应留下。
    实际看到
    O1001、O1003、O1004、O1007、O1009；其中状态可能不同。
    能证明
    channel 文本值筛选可复核，且 channel 条件不等于 paid 条件。
    不能证明
    不能证明 app 渠道订单数、渠道转化或测试订单是否应排除。
  3. 业务问题
    查看 paid_at 落在 2026-08-31 当天的订单样本。
    SQL
    SELECT order_id, user_id, paid_at FROM orders WHERE paid_at >= "2026-08-31" AND paid_at < "2026-09-01" LIMIT 5;
    预期留下
    paid_at 从 2026-08-31 00:00:00 开始，到 2026-09-01 00:00:00 之前。
    实际看到
    O1001、O1002、O1004、O1005、O1006。
    能证明
    日期边界有明确起点和结束，不靠模糊“当天”。
    不能证明
    不能证明时区、延迟刷新、NULL paid_at 或数据质量问题。
  4. 业务问题
    查看本地 orders 表中按 paid_at 倒序展示的最近订单样本。
    SQL
    SELECT order_id, user_id, paid_at FROM orders WHERE status = "paid" ORDER BY paid_at DESC LIMIT 5;
    预期留下
    status 为 paid 的行，并按 paid_at 从晚到早排列。
    实际看到
    O1019、O1014、O1018、O1018、O1013。
    能证明
    ORDER BY paid_at DESC 决定展示顺序；LIMIT 只截取前 5 行。
    不能证明
    不能证明全量趋势，也不能解释为什么 O1018 出现两次。
  5. 业务问题
    查看最近支付订单，并把 paid_at 在结果里展示成 paid_time。
    SQL
    SELECT order_id, paid_at AS paid_time FROM orders WHERE status = "paid" ORDER BY paid_at DESC LIMIT 3;
    预期留下
    结果列头出现 paid_time；原表字段仍是 paid_at。
    实际看到
    O1019、O1014、O1018，列名为 paid_time。
    能证明
    AS 能改变本次查询结果列头，帮助业务阅读。
    不能证明
    不能证明数据库字段已经改名，也不修改原表结构。
  6. 业务问题
    查看本地 orders 表中出现过哪些 channel 取值。
    SQL
    SELECT DISTINCT channel FROM orders ORDER BY channel;

    相同 channel 只展示一次。

    能证明

SESSION 02 · CHAPTER 06

责任与证据边界：先修常见误判

纠错放在学会正向查询之后。每个错误都要定位到字段或 SQL 动作。

14 MIN

看到什么，最多判断到哪里

问题太模糊
“查订单”不能执行。先补 query_id 和 business_question。
日期只写等于
paid_at 带小时分钟，应用起点和不包含的结束边界。
文本值没引号
`channel = app` 会被误读；文本值写成 `"app"`。
没排序说最新
没有 `ORDER BY paid_at DESC`，不能说第一行就是最新。
别名无意义
`paid_at AS x` 不利于交接；改成 `paid_time`。
DISTINCT 越界
`DISTINCT channel` 不等于渠道订单数或指标口径。

独立变式：修正一组基础查询差稿

同学写了 `SELECT DISTINCT user_id FROM orders LIMIT 5;`，然后说“用户数是 5，渠道指标完成”。请只用 W3D3 概念修正：补业务问题、改 SQL、写出能证明和不能证明什么。
