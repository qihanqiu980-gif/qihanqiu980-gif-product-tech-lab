SESSION 01 · CHAPTER 02

模型一：从业务问题到 WHERE 条件

数据库不能执行“帮我看看订单”。它需要你说明从哪张表开始、留下哪些行、输出哪些列。

14 MIN
Query Question

查询问题

把模糊业务话压成一条 SQL 能回答的有限问题。先说对象、范围、条件和想看的列。

从业务话到查询问题“看一下订单” → “查看本地 orders 表中 status 为 paid 的订单号、用户和支付时间”。
WHERE Condition

WHERE 条件

WHERE 是选行门。它不改变列名、不排序、不计数，只决定哪些订单行留下。

可执行条件WHERE status = "paid"
不能替代条件SELECT status FROM orders
Comparison Operator

比较符

比较符把字段和值连接成判断。等于、早于、晚于，都要变成数据库能执行的符号。

日期窗口paid_at >= "2026-08-31" AND paid_at < "2026-09-01"
Text Value Filter

文本值筛选

status、channel 这类文本值需要引号。少写引号，数据库会把 app 当成字段名而不是值。

正确WHERE channel = "app"
错误WHERE channel = app
SESSION 01 · CHAPTER 03

模型二：结果如何变得可读

筛出行之后，还要决定展示顺序、列名和去重观察。这里仍然只是在形成结果，不是在计算指标。

14 MIN
01 表FROM orders 02 选行WHERE status = "paid" 03 时间paid_at 起止边界 04 输出SELECT order_id, user_id 05 展示ORDER BY paid_at DESC 06 边界cannot_prove
Order Direction

排序方向

“最近”必须有 ORDER BY paid_at DESC。没有排序时，第一行只是当前展示第一行。

Column Alias

列别名

AS 只改结果列头，不改数据库字段。它让交接记录更容易读懂。

DISTINCT Result

DISTINCT 去重观察

DISTINCT channel 只能展示出现过哪些渠道，不能说明每个渠道有多少订单。

Evidence Boundary

证据边界

每条查询最后都要写 can_prove 和 cannot_prove，防止把样本结果说成业务结论。

SESSION 01 · CHAPTER 04

第一次复述：一条查询从问题到边界

不增加新术语。用一条完整查询把今天的学习链串起来。

10 MIN
TEACHER DEMO

查看 2026-08-31 已支付订单

这条查询只回答本地教学表中的一个样本问题，不回答收入是否正确。

SELECT order_id, user_id, status, paid_at AS paid_time
FROM orders
WHERE status = "paid"
  AND paid_at >= "2026-08-31"
  AND paid_at < "2026-09-01"
ORDER BY paid_at DESC
LIMIT 5;

复述量规

按 query_id → business_question → FROM → WHERE → SELECT/AS → ORDER BY → observed_result → cannot_prove 复述，不跳到 GROUP BY 或 JOIN。

SESSION 02 · CHAPTER 06

责任与证据边界：先修常见误判

纠错放在学会正向查询之后。每个错误都要定位到字段或 SQL 动作。

14 MIN

看到这些问题时，最多判断到哪里

问题太模糊

“查订单”不能执行。先补 business_question 和 query_id。

日期只写等于

paid_at 带小时分钟，应用起止边界，不用模糊当天。

文本值没引号

channel = app 会被误读；文本值写成 "app"。

没排序说最新

没有 ORDER BY DESC，不能说第一行就是最新。

别名无意义

paid_at AS x 不利于交接；改成 paid_time。

DISTINCT 越界

DISTINCT channel 不等于渠道订单数或指标口径。
